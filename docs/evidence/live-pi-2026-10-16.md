# Live check: Raspberry Pi server + Linux client (2026-10-16)

Target: `http://192.168.100.186:8088`, image `briani-server:messages-20261016-arm64`, qBittorrent + Prowlarr from the deployed stack. Client: Linux release/debug bundle built from `ui-redesign` HEAD (`fdcfe6b`), driven on the real Linux engine through a scratch `integration_test/` file (removed afterwards). API checks used a separate device-code session. Both test sessions were revoked at the end, and their tokens now return 401.

Media used (openly licensed, Blender Foundation, CC BY): *Sintel* (`08ada5a7a6183aae1e09d831df6748d566095a10`, 129 MB MP4) and *Tears of Steel* (`209c8226b299b308beaf2b9cd3fb49212dbd13ec`, 571 MB WebM). Info hashes were verified from WebTorrent's published `.torrent` files. Magnets carried only `xt`, `dn` and two live UDP trackers, because the server correctly rejects `ws=`/`xs=` and `url-list`.

Docker on the Pi needs sudo, so container logs and resource use were not inspected.

## Findings

Ordered by impact. File references are to this repository.

### Progressive playback (mandatory invariant) did not work in either real torrent

1. **The file tail is not fetched early.** Sintel.mp4 keeps `moov` at byte 128,641,538 (99.5%). qBittorrent reported `f_l_piece_prio=true`, yet ranges in the last 1% blocked until sequential progress reached 98% (sampled every ~20 s from 52%). The gateway serves any piece qBittorrent marks complete (`TorrentAvailability.cs`), so the gap is in which pieces get downloaded. The cause in qBittorrent/libtorrent is not determined.
2. **Eligibility ignores container metadata.** `DownloadWorker.cs:282` marks a video `eligible` once 16 MiB are contiguous. The UI showed "Ready to play" for Sintel at 26 MiB. The player then stayed on "Buffering… Waiting for more downloaded data." for 60+ s, because the `moov` was missing.
3. **Head-of-line blocking.** Tears of Steel downloaded at about 14 MB/s from 26 seeders. It went from 84% to 99.3% while contiguous bytes stayed at 10.4 MB (about 2.5 min). It became eligible at 99.8%.

### Linux desktop client

4. **The player pauses, or never starts, when the window isn't focused.** On Linux, `AppLifecycleState.inactive` was observed whenever the window lacked focus. `player_screen.dart:97-98` and `:683-685` treat anything but `resumed` as background and pause. A player opened in an unfocused window stayed at 0:00. With `resumed` simulated, the same file played normally.
5. **Download details stop refreshing when unfocused.** `download_details_screen.dart:63-72` cancels polling on `inactive`. Observed: a page stale for 6+ minutes (it showed "unknown / Fetching metadata / Transfer: Failed" while the server had moved on), and a Pause not reflected.
6. **No Resume after Pause.** qBittorrent 5 reports `stoppedUP`/`stoppedDL`, and the server maps those to `transferState: "stopped"` (`DownloadQueries.cs:487`). The client shows Resume only for `paused` (`download_details_screen.dart:868-874`), so a paused download, transferring or seeding, can only be removed. The resume action itself works (verified by API).
7. **Fake ETA.** `etaSeconds: 8640000` (qBittorrent's "infinite" value) is passed through and shown as "Time left 100d 0h" on finished torrents.
8. **Misleading pairing-expiry message (fixed in this change).** It said "The server did not explain this error", although the cause was client-side expiry.

### Server

9. **Spurious metadata timeout.** The first Tears of Steel magnet went to `stalled / metadata_timeout` 0.5 s after creation (`createdAt 08:10:57.71`, `updatedAt 08:10:58.22`), with the job generation climbing 47 → 57. The UI showed "The download failed." Retry fetched metadata in 4 s. Not root-caused (no log access).
10. **Duplicate subtitle sidecars.** A media playback session returned 18 sidecars for 9 `.srt` files: each appears once under its library id and once under its download-file id.
11. **No sidecars for download-file sessions,** even when `.srt` files are complete.
12. **`language` is null for every sidecar,** although files follow `Name.<lang>.srt`.
13. **`importState: "complete"`** was reported while the transfer was 9% done.
14. **Video thumbnails are black.** They are taken at t=0, and Sintel's first frame is black.
15. **Download name shows `unknown`** while metadata is pending, despite `dn=` in the magnet.

### Configuration (not a defect)

16. **Prowlarr has no indexers.** Discover correctly reports "No indexers are enabled…" in Latest, Most seeded and Search. No indexers were added during this check.

  - Library entries, folder navigation and scan jobs work.

  - Preferences use optimistic locking: a stale write gets 409.
  - The SSE event stream works.
- **Client playback (real engine, focus simulated):**

## Follow-up fixes (client)

Findings 4–7 are fixed in the client.
- **Focus rule:** `isForegroundLifecycle` in `lib/core/widgets/adaptive.dart` treats `inactive` as foreground on Linux, Windows and macOS only. Android phones and TV keep pausing.
  - Player, download details, the downloads list and the photo slideshow use it.
  - A hidden (minimised) window still pauses and stops polling.
- **Resume:** `canResumeDownload` in `lib/features/downloads/download_rules.dart` offers Resume for `stopped` as well as `paused`, but only once a selection exists. It is used in both the downloads list and the details page.
- **ETA:** `formatEta` shows `—` for qBittorrent's unbounded ETA.

**Tests:** `test/desktop_focus_test.dart` adds 10 tests. 6 of them fail against the previous behaviour; the other 4 guard the unchanged Android and awaiting-selection behaviour. The full suite passes 146 tests, and the analyzer is clean.

**Real-engine check:** a local dev server with a generated 90 s H.264 clip, and a throwaway integration test (since removed):
- Inactive window: playback kept advancing, from 1.1 s to 11.7 s over 10 s.

## Follow-up fixes (server)

### Root causes

These were measured on the pinned qBittorrent 5.2.4 / libtorrent 2.0.15 in an isolated Docker swarm with generated payloads (`prototypes/downloads/engine/run_piece_order_experiment.py`; 21 runs summarised in `docs/evidence/live-pi-2026-10-16-piece-order.json`).

- **Finding 1, tail not fetched early.**
  - qBittorrent re-applies first/last-piece priority right after posting file priorities (`TorrentImpl::prioritizeFiles`).
  - libtorrent rebuilds every piece priority when that asynchronous file-priority job completes (`torrent::on_file_priority`), so the boost is lost whenever the disk job finishes later.
  - Measured: in Briani's call sequence the video's last-1% span arrived at 91–100% under load or with 3 seeders, but at 3–6% in a no-`filePrio` baseline.
  - Re-sending unchanged file priorities did not help (11–25 re-sends, tail still at 91–99%).
  - **Fix:** re-assert the boost with a first/last off→on toggle, which calls only `prioritize_pieces`.
    - Measured on the three configurations that had failed: tail at 3.4%, 9.3% and 18.7%, after 1–2 toggles.
    - The worker re-asserts at most every 5 s while a wanted video lacks its assist pieces, under the job lock.
    - Playback availability refreshes now take the same lock, so a request never sees the transient "off" and fences a stream.
- **Finding 2, eligibility ignored container metadata.**
  - An MP4/MOV is now eligible, and a session `ready`, only when its whole `moov` box is verified. `Modules/Playback/MediaIndex.cs` walks top-level boxes reading verified bytes only.
  - Other containers, and unparseable files, keep the 16 MiB rule.
- **Finding 3, head-of-line blocking.**
  - Reproduced with one 8 KB/s peer: the edge stalled 15–21 s while later pieces kept arriving.
  - A stop/start nudge was measured worse (66–123 s stalls, ~12× longer completion) and rejected.
  - Not fixable within D07/D08 through qBittorrent's Web API, so it is recorded as an open owner decision in `plan/specs/11_DECISIONS_AND_RISKS.md`.
- **Finding 9, spurious metadata failure.**
  - A freshly added magnet reports `queuedDL` with `has_metadata: false` before `metaDL` (measured: about 1 s even with a free slot).
  - The worker treated any non-`metaDL` state as "metadata received", stopped the torrent and exported nothing.
  - **Fix:** it now uses qBittorrent's `has_metadata` (`serialize_torrent.cpp`), falling back to the state.

### Smaller fixes

- **Sidecars:** de-duplicated by file identity and name (finding 10). Language comes from an ISO 639 name suffix (finding 12).
- **Import state:** `importState` stays `running` until every wanted file is imported (finding 13).
- **Thumbnails:** video thumbnails seek to 10% of the duration (at most 10 minutes), with a first-frame fallback (finding 14).
- **Provisional name:** the magnet's validated `dn` (or the uploaded torrent's name) is shown until metadata arrives (finding 15).
- **ETA:** at or above qBittorrent's `MAX_ETA` (8,640,000 s, `src/base/types.h`) it is reported as unknown.

Finding 11 was a misread. Download-file sessions do list completed subtitles once their ticket is issued; the live probe looked at a session that was still `buffering`. `SubtitleApiTests.Download_sidecars_list_only_completed_subtitle_files` already covers it.
