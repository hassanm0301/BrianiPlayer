## Grouped findings for the next retry

**P1 — copied media cannot retain persisted filesystem identity.** `partial_restore` copies a partial payload into newly created `restore_data`; inherited `verify_identity_state` creates a fresh library root there. `tools/operations/briani.py:437–468` restores state/config and changes the deployment data path but does not rebind `Libraries.RootIdentity`, `TorrentJobs.ManagedRootIdentity`, or file identities. `DownloadWorker.cs:42–45` and `ContainedStorage.OpenLibrary` require those identities before resume. New directories/files have new inodes, so this schedule fails closed. Use a real config-only restore over retained original data after stopping the source, with the supported `--allow-existing-data` path, or exercise an implemented authenticated new-volume/rebind workflow. Do not edit identity columns just to pass. Evidence must call retained media retained, rather than claim copied-media recovery.

**P1 — restored guard reuses an IP still reserved by the source endpoint.** `own_network_and_seed` attaches the source guard at fixture subnet + 2. `IntegratedDrill.stop_project` stops exact containers but does not detach/delete their network endpoints. `partial_restore` attaches the distinct restored guard at the same address without detaching the old guard first. Verify and disconnect the exact recorded source guard endpoint before the new attachment, or use a distinct unused address. Preserve both guard IDs for cleanup.

**P1 — inherited image labels invalidate exact dictionary comparisons.** The initial `_seed_ready` and `cleanup_fixture` compared the seeder's entire `Config.Labels` dictionary with four harness labels. Docker image labels are retained alongside supplied labels, so LinuxServer metadata makes both comparisons fail. This prevents readiness and then prevents seeder cleanup. During review the worker introduced `validate_seed_record`, which requires the expected harness labels as a subset and additionally verifies exact ID, pinned input image reference, and the two owned bind mounts. That source correction addresses the identified schedule; no runtime pass is inferred. Newly created network label dictionaries are independent of image labels.

**P2 — recheck acceptance is weaker than the stated evidence.** The current `partial_restore` POSTs `torrents/recheck`, then waits only for a row whose state does not start with `checking`. An old stopped row can satisfy that condition before asynchronous recheck begins. Do not record `recheckBeforeResume:true` from this predicate alone. Require actual recheck observation/completion evidence, or label only the command request as observed and keep the stronger gate outstanding.

**P2 — successful cleanup metadata is evaluated before cleanup.** `run` builds its returned dictionary inside the try block, before the finally removes resources. The list field subsequently mutates, but the string `cleanup.fixtureNetworkIdRemoved` is captured as empty. `main` later adds the correct `cleanupVerification`, leaving conflicting summaries. Build the final cleanup result after cleanup, or use only the verified post-cleanup report. A failure in cleanup must retain a failed result.

**P2 — imported subprocesses are not internally bounded.** The new `docker` helper has a timeout; inherited `drill.cli`, `run_readonly`, and underlying operations subprocesses do not. A hung imported Docker/CLI call bypasses each local polling deadline. The parent must apply an owned whole-run timeout within the requested 60-minute bound and preserve cancellation/cleanup results; no whole-process bound is asserted by this review.

All findings above were sent to the parent promptly before a fresh retry.

## Previously observed helper failures and corrected contracts

The parent identified walrus binding/undefined outer-operation variables, line-separated Docker ID output parsed as JSON, wrong cleanup ownership assumptions, nonexistent `shutil.chmod`, and a `(container_id, password)` startup tuple passed as a password. The initial source read still contained the chmod/tuple errors; later reads showed `os.chmod` and `seed_password_from_startup`, validating/unpacking the exact container tuple. Metadata/operation polls now assign in the condition before returning their locally bound value and retain the returned terminal operation. `drill.docker_ids` returns a list of line-separated IDs; `inspect_json` accepts that list and returns inspected record dictionaries. No caller should reparse the list as JSON.

Actual production routes agree with the corrected harness usage: GET download files returns a plain array (`DownloadQueries.cs:313–330`); GET download list returns a page with `items`; POST download returns a 202 DownloadView; PUT selection returns a 202 DownloadView with an operation `Location`; POST actions returns a 202 OperationView. `DownloadView` contains `ownerId`, `version`, and generation `job-id:generation`, so the ownership/idempotency assertions use real fields. `verify_backup(..., deployment=True)` returns the validated manifest. `check_integrations` returns the two secret strings. The only lifecycle helper called by the new harness is its ordinary deterministic `bencode`; importing that module does not invoke its main/Docker lifecycle.

The qBittorrent wrapper uses GET for info/preferences/version/limit reads, POST for actions, and CookieJar authentication with scoped Host/Origin/Referer handling. Seeder credentials remain absent from evidence/log messages. The fixture has generated deterministic bytes and private metainfo with no trackers; its `.mp4` extension does not make it a decoder/playback test. Successful completion would establish exact restored/retained download bytes against an independent generated payload, not valid video playback or physical hardware support.
