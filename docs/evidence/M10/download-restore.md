# T25 download restore proof

**Status: bounded local T25 retained-media restore scenario passed.** The harness uses a generated 8 MiB private trackerless torrent, production upload/download APIs, and the integrated operations drill. It restores configuration into a fresh project over the same retained media root with the CLI's explicit existing-data option. It checks that the paused payload's inode and hash survive source shutdown and restored startup, observes torrent recheck completion, resumes the same request, and compares all final bytes against the generated source SHA-256.

The harness and focused tests are in [run_download_restore.py](../../../prototypes/security/resource_faults/run_download_restore.py) and [test_download_restore.py](../../../prototypes/security/resource_faults/test_download_restore.py). The fixture seeder and receiver use an owned internal Docker network with simulated public addresses. No egress policy was changed, and the probe does not contact external peers.

Validation:

The exact run artifact is [download-restore-torrent-upload-retry-v2.json](download-restore-torrent-upload-retry-v2.json), with command output in its matching `.log`.

The passing run uploaded generated private metainfo through production `POST /api/v1/torrent-uploads`, then submitted that upload ID as a `torrentUpload` request. It retained the original media root and did not copy payload bytes into the backup. The paused payload hash was `272d4dcab0b96bfc9b7114753bdba8abd7426f9b582181eac9677e7b6f0e6ba1` at inode `1931008`; after restore the same inode/hash remained, recheck was requested and its checking/completion states were observed, and the resumed file reached 8,388,608 bytes. Final receiver and generated source SHA-256 both equaled `12b5468644a0fba24de86d5145fd48bba519d4d7a4244365cc48e74078a61b7e`. The request ID, member owner, library grant, idempotency key replay, secret-key hash, and torrent infohash were preserved. The run records exact resource IDs and post-cleanup checks: both Compose projects, the fixture container/network, and scratch root were removed.

This proves configuration restore over retained media and resumed transfer with uploaded private metainfo. It does not prove full media-volume backup/restore or successful private magnet metadata bootstrap. The separate magnet diagnostic [download-restore-diagnostic.json](download-restore-diagnostic.json) is explained by official libtorrent 2.0.15 behavior: private torrents suppress the `ut_metadata` extension ([upstream source](https://raw.githubusercontent.com/arvidn/libtorrent/v2.0.15/src/ut_metadata.cpp)). That prior failure is preserved and is not relabeled as a successful magnet test.

Other preserved attempts include the initial Docker network-ID parsing failure [download-restore.json](download-restore.json) and its [cleanup correction](download-restore-cleanup-correction.json), a port-conflict preflight [download-restore-fixed.json](download-restore-fixed.json), a canceled bootstrap attempt [download-restore-final.json](download-restore-final.json), an endpoint-set assertion failure with verified cleanup [download-restore-torrent-upload.json](download-restore-torrent-upload.json), and earlier metadata-exchange diagnostics. The successful run's Docker network used the collision-checked `11.86.221.0/29` internal bridge; no public packets were sent and no host firewall or egress policy was changed.
